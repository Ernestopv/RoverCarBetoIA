# Spec — IMX500 camera (sensor with AI)

Sensor and official API reference. Everything marked as **official** comes from
the [Raspberry Pi documentation](https://www.raspberrypi.com/documentation/accessories/ai-camera.html)
and the [official Picamera2 example](https://github.com/raspberrypi/picamera2-examples/blob/main/examples/imx500/imx500_object_detection_demo.py).
What is marked as **measured** was verified on our unit.

## How it works (official)

The neural network **does not run on the Raspberry Pi**. It runs inside the sensor:

```text
Sensor IMX500
 ├── module's own ISP → crop + scaling → INPUT TENSOR → AI accelerator
 │                                                               │
 │                                          OUTPUT TENSORS ◄─────┘
 ▼
Image stream ──► Pi ISP ──► video (MediaMTX / WebRTC)
```

The sensor generates **at the same time** an image stream and an inference stream. The Pi
only receives the already-computed result.

### Concepts

| Concept | What it is |
| --- | --- |
| **Input Tensor** | The part of the sensor image that enters the network. It is produced by the ISP **of the module itself**, which crops and scales according to the ROI |
| **ROI** | Which portion of the sensor is cropped before scaling it. Units: **pixels of the sensor's full resolution**. By default: **the whole image, no crop** |
| **Output Tensors** | The result of the inference. Its shape depends on the network; the application must know how to interpret it |

**Key consequence:** the default ROI is the entire sensor (4:3), but the
video is a 16:9 crop. **The network and the video do not look at the same thing
by default**, and that is where the misalignments come from. The official solution
is to fix the ROI.

## Official `picamera2` API

| Function | What it is for |
| --- | --- |
| `IMX500.convert_inference_coords(coords, metadata, picam2)` | Converts coordinates from the input tensor space to the ISP output image space. **It is the helper that solves scaling, cropping, and translation** |
| `IMX500.set_auto_aspect_ratio()` | Computes the ROI to preserve the aspect ratio of the input tensor |
| `IMX500.set_inference_aspect_ratio(ar)` | Fixes the ROI for a given aspect ratio, e.g. that of the video |
| `IMX500.set_inference_roi_abs(rect)` | Fixes the ROI by hand in pixels of the full sensor |
| `IMX500.get_roi_scaled(metadata)` | Returns the ROI in output image coordinates |
| `IMX500.get_outputs(metadata)` | Output tensors |
| `IMX500.get_output_shapes(metadata)` | Tensor shapes |
| `IMX500.get_input_size()` | Input tensor size according to the network |
| `IMX500.network_intrinsics` | Settings declared by the network: `task`, `labels`, `bbox_normalization`, `bbox_order`, `preserve_aspect_ratio`, `postprocess`, `inference_rate` |
| `IMX500.get_kpi_info(metadata)` | DNN/DSP times for the frame |

### The official pattern

```python
imx500 = IMX500(model_file)              # before creating Picamera2
intrinsics = imx500.network_intrinsics
intrinsics.update_with_defaults()

picam2 = Picamera2(imx500.camera_num)
config = picam2.create_preview_configuration(
    controls={"FrameRate": intrinsics.inference_rate}, buffer_count=12
)
picam2.start(config)

if intrinsics.preserve_aspect_ratio:
    imx500.set_auto_aspect_ratio()

# ... per frame:
outputs = imx500.get_outputs(metadata)
boxes, scores, classes = outputs[0][0], outputs[1][0], outputs[2][0]
if intrinsics.bbox_normalization:
    boxes = boxes / input_h
if intrinsics.bbox_order == "xy":
    boxes = boxes[:, [1, 0, 3, 2]]

# and the coordinate conversion, ALWAYS through the official helper:
box = imx500.convert_inference_coords(coords, metadata, picam2)
```

### Golden rule

> **Do not compute the crop, the scaling, or the coordinate mapping by hand.**
> The sensor already crops (ROI) and the library already converts
> (`convert_inference_coords`). Any calculation of your own that duplicates that is
> a source of misalignment.

## Model catalog

23 models in `/usr/share/imx500-models/` (`imx500-models` package). The sensor
can only have **one network loaded at a time**; changing it means restarting it.

### The ones used by the official documentation

The documentation **does not catalog all 23**: it explicitly names **three**. The others
come from the same package (`imx500-all`) that it tells you to install.

| Task | Model | Where it names it |
| --- | --- | --- |
| Detection | `ssd_mobilenetv2_fpnlite_320x320_pp` | `imx500_mobilenet_ssd.json` **and** the example `imx500_object_detection_demo.py` |
| Pose | `posenet` | `imx500_posenet.json` (via `rpicam-apps`, C++) |
| Pose | `higherhrnet_coco` | example `imx500_pose_estimation_higherhrnet_demo.py` (via Picamera2) |

**Detection: the project uses `ssd_mobilenetv2_fpnlite_320x320_pp`, which is
exactly the one from the documentation.**

**Pose: of the two documented ones, `higherhrnet_coco` is chosen,** because the
`posenet` one is the `rpicam-apps` (C++) path and our backend is Python with
Picamera2. `higherhrnet_coco` is the only one with a Python decoder.

**Segmentation: `deeplabv3plus` is an inference, not a citation.** The documentation
mentions segmentation as a category in the examples repository, but does not
name the model; it is simply the only one for that task in the package.

In the following tables, ★ marks the models named by the documentation.

### Object detection

| Model | Input | inf/s | Declares |
| --- | --- | --- | --- |
| `efficientdet_lite0_pp` | 320×320 RGB | 23 | `bbox_normalization: true`, `input_aspect_ratio 1:1` |
| ★ `ssd_mobilenetv2_fpnlite_320x320_pp` | 320×320 RGB | 26 | nothing |
| `nanodet_plus_416x416_pp` | 416×416 BGR | 23 | nothing |
| `nanodet_plus_416x416` | 416×416 BGR | 23 | nothing (no post-processing on the sensor) |

All four use the same **90 COCO label entries** (80 real classes; the
rest are `"-"` gaps).

- **Chosen: `ssd_mobilenetv2_fpnlite_320x320_pp`.** It is the one used by the
  official example, it returns boxes already normalized 0..1 and does not declare
  aspect ratio handling.
- `efficientdet_lite0_pp` returns boxes in pixels and declares it with
  `bbox_normalization: true`; reading that flag backwards is what left the boxes
  misaligned. See pitfalls.
- The `nanodet` variant **without** `_pp` returns raw outputs and would force
  decoding on the Pi.

### Pose estimation

| Model | Input | inf/s | People | Decoder |
| --- | --- | --- | --- | --- |
| ★ `higherhrnet_coco` | 384×288 | 10 | up to 30 | **already exists** in picamera2 |
| ★ `posenet` | 481×353 | 30 | 1 | does not exist in Python |

`higherhrnet_coco` brings **post-processing on the sensor**: three tensors of
`[30 people, 17 keypoints]`. They are decoded with
`picamera2.devices.imx500.postprocess_higherhrnet.postprocess_higherhrnet(...,
network_postprocess=True)`, which also computes the boxes and the scores.
It requires `munkres` (`apt install python3-munkres`); the official examples also
use OpenCV (`python3-opencv`).

`posenet` has no Python decoder: it returns raw heatmaps.

### Segmentation

`deeplabv3plus` (19 inf/s): per-pixel semantic mask. It is the basis for
distinguishing traversable ground from an obstacle.

### Classification

15 ImageNet-1001 models, almost all at 30 inf/s: `efficientnet_bo`,
`efficientnet_lite0`, `efficientnetv2_b0/b1/b2`, `mnasnet1.0`, `mobilenet_v2`,
`mobilevit_xs/xxs`, `regnetx_002`, `regnety_002/004`, `resnet18`,
`shufflenet_v2_x1_5`, `squeezenet1.0`. They say *what* the whole image is, not
*where*. Not very useful for the rover.

### No task

`inputtensoronly` (65 KB): empty template that returns the input tensor
unprocessed. For debugging only.

## Pitfalls (measured on the unit)

### 1. `bbox_normalization` is read backwards

`efficientdet_lite0_pp` declares `"cpu": {"bbox_normalization": true}` and returns
values in **0..320**. It is not that the metadata lies: the flag means *"they are
pixels, they must be normalized"*, not *"they are already normalized"*. Reading it
straight produces boxes like `x[-218.97..-5.72]`.

The official example does it correctly —it divides by the input size when the flag
is active—, so with that model it would work too. `ssd_mobilenetv2_fpnlite`
declares nothing because it already returns 0..1.

### 2. `picamera2` contradicts itself on the coordinate order

Three different conventions for the same datum, within the package itself:

- `postprocess.scale_boxes` documents `[y_min, x_min, y_max, x_max]` but operates
  as if index 0 were X.
- `postprocess.scale_coords` does the opposite: it treats index 0 as Y.
- `COCODrawer.draw_keypoints` flips it again: `y0, x0 = keypoints[i][1], keypoints[i][0]`.

**Do not infer the order by reading the code: measure it.** What we measured:

- The boxes from `ssd_mobilenetv2_fpnlite` come in **`(y0, x0, y1, x1)`** (the
  default value declared by the official example, `bbox_order: "yx"`).
- The keypoints from `higherhrnet` come in **`(x, y, confidence)`**.

Check used for the keypoints, which does not depend on the documentation: a
person's two eyes are separated on the horizontal axis much more than on the
vertical, and the body of a standing person is taller than it is wide. Both criteria
pointed to the same axis.

### 3. `output[3]` is not the number of detections

It equals `[100.0]`: it is the number of *slots*. The network fills up to 100
and you must filter by score to know how many are real.

### 4. Orientation with respect to the video: no mirroring needed

The detection spec claimed that the inference runs on the raw sensor and that
therefore the boxes have to be mirrored. **It was false**, and applying it was
precisely what decentered them.

Two independent tests:

- The pose data: with a standing person, the head came out at `y = 0.21` (top)
  and the hips at `y = 0.49`. If the model saw the image without rotation, the
  180° rotation of the video would put the head **below** the hips, which is impossible.
- The definitive one: with `convert_inference_coords` and **no rotation at all**, the boxes
  fall on top of the objects in the live video. Confirmed by the user.

The official example does not mirror anything either.

## Pose: what was measured

With a real 30 s capture, `higherhrnet_coco` returned:

```text
declared shapes: [[30, 17], [30, 17], [30, 17]]
output[0] tag_k  float32   -0.94 .. 0.50     labels, quantized to 1/32
output[1] ind_k  float32     0 .. 27646      integer indices on a 192×144 grid
output[2] val_k  float32     0 .. 0.03       confidence (empty scene)
```

With a person in front, 9 of 17 joints with confidence up to 0.45, and
**coherent anatomy**: head (y=65) → shoulder (y=101) → hip (y=141), and the
wrist of the raised arm at head height with the highest confidence.
The figure occupied 34 px wide by 110 tall, the proportion of a standing person.

With nobody in the frame, the maximum confidence was 0.031: **background
noise, useful as a reference**.

At 3-4 m the network does not find the person: it works with a 384×288 input, so
you have to be at a medium distance and with the body reasonably framed.

## The real rate, measured

**What the `.rpk` declares is not what you get.** The `inference_rate` from the
metadata is the network's nominal rate, not the one the data pipeline delivers.
Measured with the same loop the backend uses:

| Model | video fps | declared `inference_rate` | New inferences per second |
| --- | --- | --- | --- |
| `ssd_mobilenetv2_fpnlite` (detection) | 30.0 (config applied; not re-probed after the fix) | 26 | — |
| `higherhrnet_coco` (pose) | **30.0** | 10 | **~5/s on the sensor, ~4/s delivered** |

> Before setting an explicit `FrameRate`, the sensor self-limited to ~17 fps and the
> pose inference dropped to ~2.7/s (it depends on the frame rate: it needs
> frames to attach results to). With `controls={"FrameRate": 30}`
> (the official example's pattern) the video rises to 30 fps and the pose inference
> goes to ~5/s on the sensor (~4/s delivered by the stack). Verified with a probe:
> at 10 fps the inference reaches its nominal rate (10/s) but the video gets worse; 30 fps
> is the balance.

Details of the same experiment:

- **The video does not run at 30 fps** even though the configuration asks for it: it
  runs at ~17 fps. The `SensorTimestamp` mark of the frames gives a median interval of 57 ms.
- **The loop reads ~17.9 metadata per second** (55.9 ms per `capture_metadata()`),
  so it is not the limiter: it is the sensor, which only attaches new inference to
  one in every six frames with `higherhrnet`.
- **The main stream format does not matter**: `RGB888` and `YUV420` give the same
  fps and the same inference rate. There is nothing to gain by changing it.
- The decoder is **not** the bottleneck: `postprocess_higherhrnet` takes
  0.2 ms with the empty scene, 1.3 ms with one person, and 30 ms in the worst case of 30
  people.

Practical consequence: a skeleton updates **three times per second**. To
follow a person slowly it is enough; in fast movements it will always look
jumpy, and that cannot be fixed from software.
